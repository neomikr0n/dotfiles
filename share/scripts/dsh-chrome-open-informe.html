Resumen ejecutivo

Script mínimo y legible que arranca dsh web si no está corriendo y abre Chrome en modo app con el token del log. Shellcheck no reporta nada, pero el flujo depende de supuestos frágiles: un sleep ciego en lugar de confirmar que el servidor levantó, y un token leído de un log fijo en /tmp que puede estar vacío u obsoleto, abriendo Chrome en silencio a una página de error.

Hallazgos por severidad

Ordenados de mayor a menor gravedad. Cada hallazgo incluye cómo corregirlo.

ALTA línea 9agente robustez

Token sin validar: puede estar vacío u obsoleto

Si dsh web ya estaba corriendo, el bloque de arranque se salta y el grep lee un log que puede no existir, estar vacío o contener el token de una sesión anterior (dsh puede rotarlo al reiniciar). El script abre igualmente Chrome con token vacío o caducado y el usuario ve una página de error sin ninguna pista de qué falló.

Cómo mejorar: Extraer el token con un bucle de reintento corto y abortar con mensaje claro a stderr si tras el timeout sigue vacío. Nunca abrir Chrome con un token que no se haya podido confirmar.

ANTES
TOKEN=$(grep -oP 'token=\K[\w-]+' /tmp/dsh-web.log | head -1)
DESPUÉS
TOKEN=""
for _ in {1..20}; do
    TOKEN=$(grep -oP 'token=\K[\w-]+' "$LOG" | head -1)
    [[ -n $TOKEN ]] && break
    sleep 0.5
done
if [[ -z $TOKEN ]]; then
    echo "No se pudo obtener el token de $LOG" >&2
    exit 1
fi
ALTA línea 5agente robustez

sleep 3 ciego: no confirma que dsh web realmente arrancó

Si dsh tarda más de 3 segundos en levantar o falla al arrancar (solo queda registrado en el log), el script continúa y abre Chrome contra un puerto muerto. El resultado es una ventana app de Chrome con error de conexión, sin diagnóstico.

Cómo mejorar: Sustituir el sleep fijo por un polling de salud: sondear http://127.0.0.1:3080/ con curl hasta que responda, con un timeout total (p. ej. 10 s) y abortar con el log si nunca responde.

ANTES
dsh web --no-open > /tmp/dsh-web.log 2>&1 &
sleep 3
DESPUÉS
dsh web --no-open > "$LOG" 2>&1 &
for _ in {1..20}; do
    curl -sf -o /dev/null http://127.0.0.1:3080/ && break
    sleep 0.5
done
if ! curl -sf -o /dev/null http://127.0.0.1:3080/; then
    echo "dsh web no respondió a tiempo; revisa $LOG" >&2
    exit 1
fi
MEDIA línea 4agente robustez

Log con ruta fija en /tmp compartido por todas las ejecuciones

/tmp/dsh-web.log es un nombre fijo: dos ejecuciones simultáneas escriben y leen el mismo archivo (carrera), una sesión vieja deja un token caducado que la siguiente ejecución lee creyendo que es válido, y el token — una credencial de sesión — queda en un archivo world-readable del directorio compartido /tmp.

Cómo mejorar: Usar ${XDG_RUNTIME_DIR:-/tmp} (runtime del usuario, 0700) y un nombre por instancia (p. ej. sufijo $$), con trap EXIT para limpiar el log temporal si ya no se necesita.

ANTES
dsh web --no-open > /tmp/dsh-web.log 2>&1 &
DESPUÉS
LOG="${XDG_RUNTIME_DIR:-/tmp}/dsh-web-$$.log"
dsh web --no-open > "$LOG" 2>&1 &
trap 'rm -f "$LOG"' EXIT
MEDIA línea 3agente robustez

Sin verificación de dependencias (lsof, dsh, google-chrome-stable)

El script asume que lsof, dsh y google-chrome-stable están en el PATH. En un entorno con PATH distinto (lanzador de teclas, systemd, Wayland session script) cualquiera puede faltar: lsof ausente hace que el if entre siempre en el arranque (duplicando instancias), y dsh o chrome ausentes producen errores crípticos.

Cómo mejorar: Comprobar las tres dependencias al inicio con command -v y salir con un mensaje específico si falta alguna.

MEDIA línea 3agente robustez

lsof :3080 no garantiza que quien escucha sea dsh

La comprobación es '¿alguien usa el puerto 3080?', no '¿está corriendo dsh web?'. Si otro servicio ocupó el puerto, el script lo asume por dsh y además envía el token por URL a ese servicio desconocido, filtrando una credencial a un tercero.

Cómo mejorar: Comprobar el proceso, no solo el puerto: verificar que existe un proceso 'dsh web' (pgrep -af) o que el PID que escucha en :3080 corresponde a dsh antes de reutilizar la instancia.

ANTES
if ! lsof -i :3080 >/dev/null 2>&1; then
DESPUÉS
if ! pgrep -af 'dsh web' >/dev/null 2>&1; then
    dsh web --no-open > "$LOG" 2>&1 &
    ...
fi
BAJA línea 1agente calidad

Cabecera mínima: sin set -euo pipefail y shebang no portable

El script no activa set -euo pipefail, así que un fallo de dsh o del grep pasa desapercibido y la ejecución continúa con estado inconsistente. El shebang /bin/bash enlaza a la ruta de Bash del sistema en vez de resolverlo vía PATH (#/usr/bin/env bash), que es lo habitual en dotfiles que pueden moverse entre máquinas.

Cómo mejorar: Usar #!/usr/bin/env bash y añadir set -euo pipefail como segunda línea. Con las validaciones ya propuestas, los errores abortarán el script en lugar de propagarse en silencio.

ANTES
#!/bin/bash
# Si dsh web no está corriendo, lo arranca
DESPUÉS
#!/usr/bin/env bash
set -euo pipefail
# Si dsh web no está corriendo, lo arranca

Sugerencias creativas

Ideas no obvias para llevar el script al siguiente nivel.

✦

Polling de salud en vez de sleep fijo

esfuerzo: bajo

Un bucle 'hasta que curl responde o expira el timeout' convierte el arranque en determinista: arranca en cuanto el servidor está listo (normalmente <1 s, más rápido que el sleep actual) y falla con diagnóstico en vez de abrir Chrome a un puerto muerto.

✦

Flag --print-url para keybindings

esfuerzo: bajo

Con getopts, un modo que solo imprime la URL (sin abrir Chrome) permite usar el script desde keybindings de Hypr/DankMaterialShell, pasarlo a otras apps, o depurar el token sin lanzar ventanas. Par de flags útiles: --port y --browser para parametrizar los valores hoy hardcodeados.

✦

Validar el token contra el servidor antes de abrir Chrome

esfuerzo: medio

Un curl con el token que compruebe el código HTTP distingue token válido de caducado. Si es inválido, el script puede reiniciar dsh web y regenerar el token: convierte el caso 'log viejo' en auto-reparación en vez de fallo silencioso.

✦

Función log_msg + notificación de escritorio

esfuerzo: bajo

Como este script vive en un entorno de escritorio (DankMaterialShell), un log_msg que escriba a stderr con nivel y además envíe notify-send en los fallos haría el error visible en pantalla en lugar de solo en /tmp. Beneficio inmediato: el usuario sabe por qué Chrome no abrió la app.

✦

Ciclo de vida explícito de dsh web

esfuerzo: medio

Decidir si dsh web debe vivir mientras Chrome esté abierto: con un trap EXIT que mate al proceso hijo si fue arrancado por este script, la instancia no queda huérfana tras cerrar el navegador. Alternativa: modo --keep para dejarlo corriendo como servicio de sesión.

Puntos ciegos

Riesgos que ni shellcheck ni una lectura rápida detectan.

◉

Carrera entre dos instancias del script

Riesgo: Si el keybinding se dispara dos veces seguido (doble pulsación, launchers repetidos), ambas ejecuciones comprueban el puerto a la vez, ambas arrancan dsh web y ambas escriben el mismo /tmp/dsh-web.log: una truncó el log justo cuando la otra hacía grep, y pueden quedar dos procesos dsh peleándose por el puerto.

Mitigación: Log por instancia ($$ o mktemp) y lock exclusivo con flock en un fd (exec 9>lock; flock -n 9 || exit 0) para que la segunda ejecución simplemente salga o espere.

◉

Token obsoleto cuando dsh ya estaba corriendo

Riesgo: Es el caso más probable en el uso diario: dsh web ya corre de una sesión anterior, el bloque de arranque se salta, y el token del log viejo puede haber sido rotado. Chrome abre una página de error y nada en el sistema indica por qué. Si el log ni siquiera existe, grep escribe su error por stderr rompiendo la estética del launcher.

Mitigación: Validar el token con curl antes de abrir Chrome y, si falla, reiniciar dsh web para regenerarlo (o al menos notificar el fallo con notify-send). Suprimir stderr del grep (2>/dev/null) y tratar log ausente como error controlado.

◉

Puerto 3080 ocupado por otro servicio

Riesgo: Cualquier otro proceso que escuche en 3080 hace creer al script que dsh está activo. Además de abrir la app equivocada, el token viaja en la URL a ese servicio tercero: es una fuga real de credencial, no solo un fallo funcional.

Mitigación: Verificar la identidad del proceso que escucha (pgrep -af 'dsh web' o cruzar el PID de lsof con /proc/PID/cmdline) y, si no es dsh, abortar con error en vez de reutilizar el puerto.

◉

Supuestos sobre el formato del log de dsh

Riesgo: El regex 'token=\K[\w-]+' depende de que dsh escriba el token en ese formato exacto y en la primera línea donde aparece. Una actualización de dsh que cambie el formato, o un log con varias sesiones acumuladas, rompe la extracción en silencio (head -1 puede quedarse con el token de una sesión vieja si el log no se trunca).

Mitigación: Comprobar que el token extraído es no vacío y, si el formato cambia, fallar con mensaje que apunte al log. Preferir truncar/rotar el log en cada arranque y documentar de qué línea de dsh se espera el token.

◉

dsh web queda huérfano si el script se interrumpe

Riesgo: El proceso dsh se lanza en background sin trap ni registro de PID. Si el script muere a mitad (Ctrl-C, kill del launcher), dsh sigue corriendo adjunto a la sesión; y como el log quedó en /tmp con nombre fijo, la siguiente ejecución hereda un log que puede no corresponder al proceso vivo actual.

Mitigación: Guardar el PID hijo ($!) junto al log por instancia y usar trap EXIT para decidir el ciclo de vida: matarlo si el script murió antes de abrir Chrome, o dejarlo con --keep si el usuario quiere la sesión persistente.
