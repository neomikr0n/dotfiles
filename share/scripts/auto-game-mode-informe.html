Resumen ejecutivo

Script muy sólido: wrapper bash mínimo que delega en Python embebido, con shellcheck limpio, atomicidad en el estado, protección contra PID reuse vía starttime y limpieza en finally. Los hallazgos son de segundo orden: decodificación UTF-8 estricta de /proc que puede matar el monitor, falta de validación de state.json corrupto y algunas condiciones muertas o carreras estrechas.

Hallazgos por severidad

Ordenados de mayor a menor gravedad. Cada hallazgo incluye cómo corregirlo.

Lecturas de /proc con UTF-8 estricto pueden tumbar el monitor

comm admite bytes arbitrarios (salvo '/' y NUL) y no está garantizado que sea UTF-8 válido. read_text() lanza UnicodeDecodeError (subclase de ValueError) al encontrar un proceso con nombre binario. En game_reasons el ValueError se captura, pero pause_wallpapers (líneas 131, 138, 150) y restore (línea 183) solo capturan ProcessLookupError/PermissionError/FileNotFoundError, así que un solo proceso con comm exótico mata el ciclo con traceback y termina el monitor.

Cómo mejorar: Leer como bytes y decodificar con reposición de errores: (path / 'comm').read_bytes().decode('utf-8', 'replace'). Aplicarlo también en identity() para stat.

ANTES
fields = (path / 'stat').read_text().rsplit(')', 1)[1].split()
...
comm = (path / 'comm').read_text().strip()
DESPUÉS
stat_text = (path / 'stat').read_bytes().decode('utf-8', 'replace')
fields = stat_text.rsplit(')', 1)[1].split()
...
comm = (path / 'comm').read_bytes().decode('utf-8', 'replace').strip()

state.json corrupto bloquea la recuperación hasta borrado manual

Manager.__init__ hace json.loads sin validación: un state.json truncado (corte de luz, disco lleno) lanza JSONDecodeError y un JSON válido sin las claves esperadas lanza KeyError al acceder a self.state['paused']. La instancia no arranca, no restaura y los wallpapers quedan congelados hasta que el usuario borra el archivo a mano.

Cómo mejorar: Envolver la carga en try/except (ValueError, KeyError, TypeError): si falla, renombrar el archivo a state.json.corrupt, arrancar con estado vacío y avisar por log de que hay cambios sin restaurar. Validar que las claves 'session', 'options' y 'paused' existan con los tipos esperados.

ANTES
if self.path.exists():
    self.state = json.loads(self.path.read_text())
DESPUÉS
if self.path.exists():
    try:
        loaded = json.loads(self.path.read_text())
        assert isinstance(loaded.get('options'), dict)
        assert isinstance(loaded.get('paused'), list)
        self.state = loaded
    except (ValueError, AssertionError, AttributeError):
        self.path.rename(self.path.with_suffix('.json.corrupt'))
        log('state.json ilegible; renombrado. Revisa wallpapers detenidos.')

Condición muerta y confusa al respetar el modo manual ML4W

'if previous not in (0, 1) or previous == 0: continue' es redundante: si previous es 0 ya lo excluye 'not in (0, 1)', y None (hyprctl falló) también cae ahí. La intención real es 'solo actuar si está activado (=1)', pero tal como está escrita obliga a descifrarla y invita a romperla al editar.

Cómo mejorar: Simplificar a una comparación directa y comentar la intención.

ANTES
if previous not in (0, 1) or previous == 0:
    continue
DESPUÉS
if previous != 1:  # sólo guardar/restaurar efectos que estaban activados
    continue
BAJA línea 184agente robustez

restore() reanuda procesos que el usuario pudo parar a mano

restore() envía SIGCONT a todo lo que esté en 'paused' sin comprobar el estado actual. Si el usuario hizo SIGSTOP manual del wallpaper entre la pausa y la restauración (o el proceso estaba 'T' por otra razón), el script lo despierta contra su voluntad. El lado de pausa sí comprueba el estado ('T', 't', 'Z'); el de restauración no es simétrico.

Cómo mejorar: Antes del SIGCONT, leer identity(path) y saltar el SIGCONT si el estado es 'T' o 't' (y descartar el registro igualmente, pues ya no lo gestionamos).

ANTES
if path.stat().st_uid == UID and identity(path)[0] == record['start']:
    os.kill(record['pid'], signal.SIGCONT)
DESPUÉS
if path.stat().st_uid == UID and identity(path)[0] == record['start']:
    if identity(path)[1] not in ('T', 't'):
        os.kill(record['pid'], signal.SIGCONT)
BAJA línea 150agente robustez

IndexError de identity() sin capturar en pause_wallpapers y restore

identity() puede lanzar IndexError si /proc/PID/stat desaparece o se trunca entre la lectura y el split. game_reasons lo captura, pero los except de pause_wallpapers (línea 157) y restore (líneas 185-188) no incluyen IndexError, así que una carrera estrecha aborta el ciclo completo en vez de saltar ese PID.

Cómo mejorar: Añadir IndexError a las tuplas de excepción de ambos métodos (o capturar (OSError, IndexError) ya que estadísticamente son el mismo caso: el proceso ya no está).

ANTES
except (ProcessLookupError, PermissionError, FileNotFoundError):
    continue
DESPUÉS
except (ProcessLookupError, PermissionError, FileNotFoundError, IndexError):
    continue
BAJA línea 156agente robustez

Carrera de reutilización de PID entre identity() y SIGSTOP

En pause_wallpapers, entre leer starttime (línea 150) y os.kill(SIGSTOP) puede morir el proceso y reutilizar su PID. El SIGSTOP golpearía a un proceso inocente cuyo starttime no coincide con el registro, y restore() nunca lo reanudaría: ese proceso quedaría detenido para siempre. La ventana es microscópica pero el daño es permanente.

Cómo mejorar: Releer /proc/PID/stat inmediatamente antes del kill y comprobar que el starttime sigue coincidiendo con el que se acaba de guardar; si no, descartar el registro.

ANTES
record = {'pid': int(path.name), 'start': start}
self.state['paused'].append(record)
self.save()
os.kill(record['pid'], signal.SIGSTOP)
DESPUÉS
record = {'pid': int(path.name), 'start': start}
if identity(PROC / path.name)[0] != start:
    continue  # el PID cambió de dueño entre lecturas
self.state['paused'].append(record)
self.save()
os.kill(record['pid'], signal.SIGSTOP)
BAJA línea 123agente robustez

save() sin fsync: corte de luz puede dejar state.json vacío

write_text + replace es atómico frente a crashes del proceso, pero no frente a pérdida de energía: los datos pueden no haber llegado a disco cuando se hace el rename, dejando un state.json vacío en el peor momento (justo tras pausar wallpapers). Se conecta con el hallazgo del estado corrupto.

Cómo mejorar: Abrir el temporal en modo binario, escribir, flush y os.fsync(fileno) antes de replace.

ANTES
temporary = self.path.with_suffix('.tmp')
temporary.write_text(json.dumps(self.state))
temporary.replace(self.path)
DESPUÉS
temporary = self.path.with_suffix('.tmp')
with temporary.open('w') as handle:
    handle.write(json.dumps(self.state))
    handle.flush()
    os.fsync(handle.fileno())
temporary.replace(self.path)

Doble lectura de environ para PIDs ya detectados por SteamLaunch

Cuando un PID ya revela su AppId por cmdline (SteamLaunch), se sigue leyendo y parseando su environ en la misma iteración. Además, cada ciclo lee cmdline de todos los procesos del usuario cada 5 segundos, lo que es asumible pero prescindible para PIDs ya descartados con el mismo starttime.

Cómo mejorar: Hacer 'continue' tras añadir el hallazgo por cmdline cuando el AppId ya coincidió, y opcionalmente cachear (pid, starttime) de procesos descartados para no reescanearlos en cada ciclo.

if re.fullmatch(rb'AppId=[1-9][0-9]*', argument) and argument.split(b'=', 1)[1] not in NON_GAME_APPIDS:

El wrapper no comprueba que python3 exista

exec python3 falla con un mensaje críptico de bash si python3 no está en PATH (instalación mínima, chroot, PATH roto en cron/systemd).

Cómo mejorar: Verificar con command -v antes del exec y dar un mensaje claro.

ANTES
exec python3 - "$@" <<'PYTHON'
DESPUÉS
command -v python3 >/dev/null 2>&1 || { echo 'auto-game-mode: python3 no está disponible' >&2; exit 127; }
exec python3 - "$@" <<'PYTHON'

Sugerencias creativas

Ideas no obvias para llevar el script al siguiente nivel.

✦

Modo --once para probar reglas de detección sin arrancar un juego

esfuerzo: bajo

Un flag --once que ejecute un único ciclo de detección (clients + game_reasons) e imprima si activaría el modo juego y por qué, sin tocar hyprctl keyword ni SIGSTOP. Hoy verificar un AppId nuevo obliga a arrancar el juego de verdad o usar --check a mano; con --once la prueba es de ida y vuelta y sirve para validar cambios en HELPERS/NON_GAME_APPIDS.

✦

Configuración externalizada en ~/.config/auto-game-mode.json

esfuerzo: medio

HELPERS, NON_GAME_APPIDS, OPTIONS y los nombres de compositores están hardcodeados. Un JSON de usuario (con valores por defecto si no existe) permitiría añadir el AppId de una launcher no-Steam o un nuevo helper sin editar el script, y el fichero versionable en dotfiles serviría de documentación de qué se considera 'juego'.

✦

Unidad systemd --user con Restart=on-failure

esfuerzo: bajo

Si el script muere con SIGKILL (OOM mientras un juego devora RAM, crash de Python), el finally no corre y los wallpapers quedan congelados hasta que el usuario lo relaanza. Una unidad systemd user (ExecStart=auto-game-mode.sh, Restart=on-failure) garantiza que el siguiente arranque ejecuta la rama de recuperación del estado pendiente sin intervención manual, y simplifica el arranque automático con la sesión.

✦

Resumen de sesión: tiempo total en modo juego

esfuerzo: bajo

Al restaurar, log('Modo juego OFF...') podría incluir cuánto tiempo duró el modo juego (timestamp en state.json al activar). Es telemetría gratis con los datos que ya persistes, y ayuda a afinar AUTO_GAME_EXIT_DELAY viendo cuántas restauraciones se disparan por salidas breves.

✦

Verbosidad graduable con AUTO_GAME_VERBOSE

esfuerzo: bajo

log() imprime poco: en una sesión con problemas no sabes qué PIDs se examinaron ni por qué se descartó un wallpaper (otra sesión, estado T, AppId excluido). Un nivel verbose que trace las decisiones de game_reasons y pause_wallpapers convertiría los puntos ciegos de /proc en diagnóstico visible.

✦

Deshidratación progresiva en vez de SIGSTOP binario

esfuerzo: alto

Hoy el wallpaper pasa de 100% a 0% de golpe con SIGSTOP. Para fondos con audio o transiciones, una alternativa suave es primero enviar la señal de pausa propia del backend (mpv: SIGSTOP ya, pero gslapper podría aceptar un hyprctl plugin/dispatch) y reservar SIGSTOP como último recurso, dejando el comportamiento registrado en state.json para restaurar exactamente lo que se pausó.

Puntos ciegos

Riesgos que ni shellcheck ni una lectura rápida detectan.

◉

Muerte con SIGKILL deja wallpapers congelados indefinidamente

Riesgo: El camino de recuperación depende del finally o de que el usuario vuelva a ejecutar el script. Si el OOM killer o un kill -9 se lo lleva por delante durante una sesión de juego intensiva, los wallpapers quedan en SIGSTOP y las opciones de Hyprland en 0 hasta que alguien lance el script de nuevo; si el usuario no lo hace (porque cree que sigue vigilando), el escritorio queda degradado para siempre.

Mitigación: Guardar un timestamp en state.json y, en --status, avisar con claridad ('recuperación pendiente desde hace N minutos'); mejor aún, unidad systemd --user con Restart=on-failure que ejecute la rama de recuperación automáticamente.

◉

hyprctl puede apuntar a otra instancia de Hyprland

Riesgo: El script solo comprueba que HYPRLAND_INSTANCE_SIGNATURE no esté vacía. Si se lanza desde un contexto cuya instancia heredada ya no existe (sesión anterior, export en un .profile, lanzamiento desde otra sesión del mismo usuario), hyprctl usará ese socket y getoption/keyword consultarán y cambiarán los efectos del compositors equivocado, mientras la detección de wallpapers filtra por la SESSION vieja y no encuentra nada.

Mitigación: Tras el arranque, validar que 'hyprctl -j activewindow' o 'hyprctl version' responda para ESA instancia antes de entrar al bucle, y abortar con mensaje si no.

◉

environ de procesos ajenos puede no ser UTF-8 y el parseo asume formato

Riesgo: game_reasons parsea environ como pares clave=valor binarios y decodifica argumentos con .decode() sin errores='replace' (línea 98). Un argumento AppId con bytes raros lanzaría UnicodeDecodeError dentro de found.add, que sí está cubierto por el except ValueError del bloque... pero solo porque ese except es tan amplio que también se tragaría bugs reales de lógica, ocultándolos silenciosamente ciclo tras ciclo.

Mitigación: Decodificar con errors='replace' en los .decode() de datos de /proc y estrechar los except a los errores esperados, dejando que los inesperados logged con traceback en modo verbose.

◉

Duplicados de compositores rompen el fallback de PermissionError

Riesgo: En pause_wallpapers, el fallback 'si el único compositor es Hyprland, pausar aunque Yama bloquee environ' compara compositors != ['Hyprland']. Con dos instancias de Hyprland del mismo usuario la lista es ['Hyprland', 'Hyprland'] y el fallback se desactiva (conservador, bien); pero si el usuario corre nested Hyprland dentro de otro compositors de la lista, la sesión real del juego puede quedar fuera del filtro y el fondo de la sesión anfitriona se pausa o se ignora de forma no obvia.

Mitigación: Usar un set en vez de lista y registrar en log (verbose) cuándo se aplica el fallback y qué compositores se vieron, para que el comportamiento sea diagnosticable.

◉

AUTO_GAME_INTERVAL inválido produce un error críptico

Riesgo: float(os.environ.get('AUTO_GAME_INTERVAL', '5')) lanza ValueError que el try del __main__ convierte en 'Error: could not convert string to float: ...' y salida 1. En un lanzamiento desde Hyprland exec-once el usuario no ve el mensaje y el script simplemente 'no funciona'.

Mitigación: Parsear con try/except propio y parser.error() con mensaje accionable que incluya el valor recibido y el rango válido.
